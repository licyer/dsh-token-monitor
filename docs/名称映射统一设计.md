# 名称映射统一设计

> 状态：设计稿（待评审）
> 目标版本：1.2.0
> 前置约束：**数据源保持原样，映射只发生在读取/展示层**——不迁移数据、不加 raw 列、不落库归一。

---

## 1. 目标与硬约束

一句话：**库里存什么就是什么，映射只在读出来之后做。**

| 目标 | 说明 |
|---|---|
| 单一权威 | 新增/修改一个提供方、厂商、模型，只改**一个 JS 文件** |
| 全链路一致 | 聚合、筛选、取价、展示四个环节用同一套规范身份 |
| 脏数据自愈 | 历史别名、跨设备导入、第三方写法，读取时投影，**源数据一个字节不动** |
| 可反复迭代 | 映射规则改了，直接重启生效，历史数据自动按新规则重新解释 |
| 未知不猜 | 认不出的名字原样显示并标记「未收录」，绝不静默合并 |
| 前后端同源 | 客户端不再维护自己的映射表，由服务端下发同一份 |

**硬约束（本设计的红线）**

1. `usage_requests` / `usage_daily_rollups` 的 `provider` / `model` 列**永远写入源里的原值**；
2. 不做数据迁移、不加 `raw_*` 列、不改主键；
3. 归一化只存在于「查询结果 → 响应」这一段；
4. 唯一例外：源里**缺少** provider 时（CC 的 `_session` 行）补一个归属值——这是补缺，不是改名。

### 3.1 一个文件：`lib/util/mapping-registry.js`（映射登记）

纯数据 + 纯函数，**不碰数据库、不碰文件、不碰网络**。

**字段约定**

| 字段 | 说明 |
|---|---|
| `label` / `display` | 字符串，或 `{ zh, en }` |
| `vendor` | 上级厂商 id |
| `aliasOf` | 该 id 是某规范 id 的别名（provider 用） |
| `aliases` | 等价写法（model 用），比较时大小写不敏感、忽略首尾空白 |
| `kind` | provider：`quota` / `balance`；vendor：`owner` / `reseller` / `unknown` |
| `displayAs` | 统计口径的显示名（只 `deepseek-account` 用到） |
| `urls` / `fetch` | 官网链接 / 抓取器名 |
| `color` | 厂商基础色；`null` = 不占色系 |
| `order` | 显式排序 |

### 3.2 归一算法（纯函数，读取期执行）

```
canonicalProvider(raw) →
  1. 去首尾空白、小写 → 精确命中 PROVIDERS？
  2. 命中 aliasOf → 追一次到规范 id
  3. 未命中 → 返回原值（未知）

canonicalModel(raw) →
  1. 去空白，大小写不敏感地查 MODELS 与 aliases
  2. 未命中 → 去掉最后一个 '/' 之前的 vendor 前缀再查一次
  3. 仍未命中 → 返回 { id: 原值, display: 原值, known: false }
     并可附带 prefixVendor（仅用于配色分组，不改名字）
```

第 3 步刻意**只推断厂商、不改模型名**：名字不认识就不冒充别的模型（`deepseek-flash` ≠ `deepseek-v4-flash`）。

### 3.3 投影层：唯一入口 `project()`

服务端所有返回用量数据的端点，都必须经过这一层：

```js
// 一条用量行 → 规范身份 + 展示信息
project(provider, model) → {
  provider,            // 规范 providerId
  model,               // 规范模型 id
  providerLabel,       // 展示名（displayAs 优先）
  modelLabel,          // 模型展示名（未知则原值）
  vendor,              // 所属厂商
  vendorLabel,
  known,               // 是否收录
}
```

所有端点保证：**返回的每一行都带 label**，前端不再做任何名称处理。

### 3.4 聚合与筛选：SQL 取原值 → JS 归并

这是"不改库"的关键实现方式。

**聚合（distribution / rank / by-model）**

```sql
-- 仍然按库里的原值分组（不归一，SQL 保持简单）
SELECT provider, model, SUM(...) FROM usage_daily_rollups GROUP BY provider, model
```

拿到结果后在 JS 里二次聚合：

```js
const merged = new Map();
for (const r of rawRows) {
  const p = project(r.provider, r.model);
  const key = `${p.vendor}|${p.model}`;   // 按规范身份归并
  merge(merged, key, r);                   // 数值相加，模型名单去重
}
```

代价：分组行数从"模型数"变成"（原值组合数）"。当前库里是 13 组、几十行量级，可以忽略；即使上千行也只是内存 Map。

**筛选**

用户选的是规范模型/厂商，而库里是原值 → 请求时把规范值展开成原值集合：

```js
// 缓存：SELECT DISTINCT provider, model FROM usage_daily_rollups（几百行，同步后失效）
expandModel(canonical) → ['k3', 'Kimi-K3', 'moonshotai/Kimi-K3']
expandVendor(vendor)   → ['kimi-coding', 'moonshotai-cn', …]
```

SQL 用 `IN (?, ?, …)` 过滤，**分页不受影响**（明细表的 LIMIT/OFFSET 仍在 SQL 里）。

DISTINCT 缓存挂在 store 上，每轮折叠/导入后清空；缓存缺失时降级为"只查规范值本身"，不会报错。

### 3.5 前后端同源

`mapping-registry.js` 只在服务端 import。客户端需要的部分由端点下发：

```
GET /token-monitor/mappings
→ {
    ok: true,
    vendors:   { deepseek: { label, order, color, kind }, … },
    providers: { 'kimi-coding': { vendor, label, urls }, … },
    clients:   { dsh: 'DSH', … },
    models:    { k3: { display: 'Kimi K3', vendor: 'kimi' }, … },
    unknown:   { label: { zh: '未知', en: 'Unknown' } }
  }
```

客户端启动拉一次并缓存；拉不到时**降级为显示原始 id**（不内置一份表、不崩溃）。

### 3.6 数据流

```
源日志 / CC 库 / 导入文件
        │  原样写入（只补缺失的 provider）
        ▼
   ┌─────────┐
   │  数据库  │   provider / model 永远是源里的原值
   └─────────┘
        │  SQL 按原值分组 / 过滤
        ▼
   原始聚合结果
        │  project() 归一到规范身份 + 生成 label
        ▼
   规范聚合结果 + label
        │  JSON
        ▼
   页面（只渲染，不做任何映射）
```

**换映射规则的成本**：改 `mapping-registry.js` → 重启 → 所有页面按新规则重新解释历史数据。零迁移、零重扫。

### 3.7 明确不做

| 不做 | 原因 |
|---|---|
| 入库归一（fold / 导入改名） | 会覆盖源数据，映射规则不可回溯 |
| 加 `raw_*` 列、做数据迁移 | 源数据本来就没被改，不需要保留副本 |
| 改动会话日志 | 原始事实，永久保留原样 |
| 猜模型等价 | 名字不认识绝不合并 |
| 在线拉模型目录 | pi-ai 只作厂商推断与刊例价兜底，不作身份权威 |

> 注：`fold.js` 现有的 `PROVIDER_NORM` 与 `import-cc.js` 的 provider 归一属于历史实现，本次改为读取期投影后应**移除**（已入库的历史归一名不影响：投影层对规范名是幂等的）。

### S2 落地要点（供 S3 参考）

- **聚合**：SQL 仍按库里原值 `GROUP BY`，拿到结果后 `mergeBy()` 按规范身份二次合并 —— 同一模型的不同写法归并成一行/一根柱子，**总 token 前后一致**（已核对 5,283,729,616 不变）。
- **筛选**：`pushModelCond()` / `providerCond()` 把规范值展开成"库内实际出现过的原始值集合"，SQL 用 `IN (…)`，分页不受影响；组合缓存 60s，折叠/导入后主动失效。
- **下发**：新增 `GET /token-monitor/mappings`（vendors/providers/clients/models + label/color/order/kind），旧 `/provider-mappings` 保留一版兼容。
- **入库**：`fold.js` 的 `PROVIDER_NORM` 与 `import-cc.js` 的 provider 归一已删除，源值原样入库；`import-cc` 只在源**缺少** provider（`_session` / UUID 实例）时按登记表补归属。
- **取价**：`pricing.js` 改走 `priceKeyOf()`，`moonshotai/Kimi-K3` 与 `k3` 现在用同一档 CNY 价（此前一个走表价、一个走 pi-ai 美元价）。

## 7. 已定结论

| # | 问题 | 结论 |
|---|---|---|
| 1 | **颜色放哪** | 放 `mapping-registry.js` 的 `VENDORS[].color`（一处），经 `/token-monitor/mappings` 下发；客户端删掉 `VENDOR_COLORS`。理由：颜色是厂商的展示属性，和 label 同源；插件前后端同仓库同版本发布，不存在"服务端不认识新颜色"的情况 |
| 2 | **i18n** | 名称直接在登记表里写 `{ zh, en }`，`resolveLabel(label, lang)` 取值；client 的 `VENDOR_I18N_KEYS` 与 `vendor.*` 文案键删除。理由：登记表是名称权威，名称的多语言版本就该在这里；i18n key 只是把同一份数据搬到了另一个文件 |
| 3 | **未知模型/提供方** | **正常显示原始 id，不加「未收录」标记**；随着版本迭代逐步补登记。`known` 字段仍返回，仅作内部诊断用，前端不显示任何标记 |
| 4 | **筛选展开** | 服务端把规范值展开成 `IN (原值集合)` 查询，此设计即最终方案 |

### 红线：登记表决定"怎么显示"，不决定"是否存在"

**未登记 ≠ 隐藏，未登记 ≠ 改名。**

| 场景 | 要求 |
|---|---|
| 未登记的模型 `brand-new-model-x` | 原样显示 `brand-new-model-x`；参与聚合、参与筛选；`known:false` 只作诊断 |
| 未登记的提供方 `new-provider` | 原样显示 `new-provider`；vendor 回退为自身；不并入 `unknown` |
| 登记表整表加载失败 | 全部原样显示（降级），页面仍可用 |
| 新增登记 | 只影响显示与归属，不影响任何已存在的数据行 |

已有测试固定这条：`test/mapping-registry.test.js` 的「未登记的模型/提供方不会被隐藏或改写」。

## 8. 变更自由度（本设计的核心收益）

| 场景 | 现在的代价 | 新设计的代价 |
|---|---|---|
| 发现两个名字其实是同一个模型 | 改 2 张表 + 已有统计仍分开 | 加一行 `aliases`，重启 |
| 想把某模型改归厂商 | 改正则 + 重启 | 改 `vendor` 字段，重启 |
| 跨设备导入带进新写法 | 库里多一行脏数据，页面显示裸名 | 投影层直接归并，无需处理 |
| 映射改错了 | 库里已被改写，回不去 | 改回来重启即可，历史数据从未被动过 |
